# Интернет-магазин «Web-Larёk»
«Web-Larёk» — это интернет-магазин с товарами для веб-разработчиков, где пользователи могут просматривать товары, добавлять их в корзину и оформлять заказы. Сайт предоставляет удобный интерфейс с модальными окнами для просмотра деталей товаров, управления корзиной и выбора способа оплаты, обеспечивая полный цикл покупки с отправкой заказов на сервер.

## Архитектура приложения

Код приложения разделен на слои согласно парадигме MVP (Model-View-Presenter), которая обеспечивает четкое разделение ответственности между классами слоев Model и View. Каждый слой несет свой смысл и ответственность:

Model - слой данных, отвечает за хранение и изменение данных.  
View - слой представления, отвечает за отображение данных на странице.  
Presenter - презентер содержит основную логику приложения и  отвечает за связь представления и данных.

Взаимодействие между классами обеспечивается использованием событийно-ориентированного подхода. Модели и Представления генерируют события при изменении данных или взаимодействии пользователя с приложением, а Презентер обрабатывает эти события используя методы как Моделей, так и Представлений.

### Базовый код

#### Класс Component
Является базовым классом для всех компонентов интерфейса.
Класс является дженериком и принимает в переменной `T` тип данных, которые могут быть переданы в метод `render` для отображения.

Конструктор:  
`constructor(container: HTMLElement)` - принимает ссылку на DOM элемент за отображение, которого он отвечает.

Поля класса:  
`container: HTMLElement` - поле для хранения корневого DOM элемента компонента.

Методы класса:  
`render(data?: Partial<T>): HTMLElement` - Главный метод класса. Он принимает данные, которые необходимо отобразить в интерфейсе, записывает эти данные в поля класса и возвращает ссылку на DOM-элемент. Предполагается, что в классах, которые будут наследоваться от `Component` будут реализованы сеттеры для полей с данными, которые будут вызываться в момент вызова `render` и записывать данные в необходимые DOM элементы.  
`setImage(element: HTMLImageElement, src: string, alt?: string): void` - утилитарный метод для модификации DOM-элементов `<img>`


#### Класс Api
Содержит в себе базовую логику отправки запросов.

Конструктор:  
`constructor(baseUrl: string, options: RequestInit = {})` - В конструктор передается базовый адрес сервера и опциональный объект с заголовками запросов.

Поля класса:  
`baseUrl: string` - базовый адрес сервера  
`options: RequestInit` - объект с заголовками, которые будут использованы для запросов.

Методы:  
`get(uri: string): Promise<object>` - выполняет GET запрос на переданный в параметрах ендпоинт и возвращает промис с объектом, которым ответил сервер  
`post(uri: string, data: object, method: ApiPostMethods = 'POST'): Promise<object>` - принимает объект с данными, которые будут переданы в JSON в теле запроса, и отправляет эти данные на ендпоинт переданный как параметр при вызове метода. По умолчанию выполняется `POST` запрос, но метод запроса может быть переопределен заданием третьего параметра при вызове.  
`handleResponse(response: Response): Promise<object>` - защищенный метод проверяющий ответ сервера на корректность и возвращающий объект с данными полученный от сервера или отклоненный промис, в случае некорректных данных.

#### Класс EventEmitter
Брокер событий реализует паттерн "Наблюдатель", позволяющий отправлять события и подписываться на события, происходящие в системе. Класс используется для связи слоя данных и представления.

Конструктор класса не принимает параметров.

Поля класса:  
`_events: Map<string | RegExp, Set<Function>>)` -  хранит коллекцию подписок на события. Ключи коллекции - названия событий или регулярное выражение, значения - коллекция функций обработчиков, которые будут вызваны при срабатывании события.

Методы класса:  
`on<T extends object>(event: EventName, callback: (data: T) => void): void` - подписка на событие, принимает название события и функцию обработчик.  
`emit<T extends object>(event: string, data?: T): void` - инициализация события. При вызове события в метод передается название события и объект с данными, который будет использован как аргумент для вызова обработчика.  
`trigger<T extends object>(event: string, context?: Partial<T>): (data: T) => void` - возвращает функцию, при вызове которой инициализируется требуемое в параметрах событие с передачей в него данных из второго параметра.

## Данные
В системе выделены две базовые модели данных, вокруг которых строится логика приложения: товар и покупатель.

## Сущность «Товар» (IProduct)
Интерфейс IProduct задаёт шаблон данных для каждого отдельного товара в каталоге. Он содержит всю информацию, которая требуется для отображения карточки товара и дальнейшей работы с ним в разных частях интерфейса — от витрины до корзины.

Ключевые характеристики:

id: string — уникальный идентификатор, позволяющий однозначно отличать один товар от другого и использовать его для поиска и отслеживания состояния.
title: string — наименование товара, которое выводится в списке каталога, в карточке и в корзине.
description: string — развёрнутое описание, раскрывающее особенности и назначение продукта.
image: string — ссылка на изображение, используемая для визуального представления товара.
category: string — категория, к которой отнесён товар; помогает в фильтрации и группировке позиций.
price: number | null — стоимость товара. Значение null сигнализирует о том, что цена временно недоступна или товар не продаётся.
Сущность «Покупатель» (IBuyer)
Интерфейс IBuyer описывает профиль клиента, который оформляет заказ. В нём собраны все сведения, необходимые для обработки покупки и коммуникации с пользователем.

Основные поля:

payment: TPayment — способ оплаты, строго ограниченный допустимыми вариантами через тип TPayment.
address: string — адрес доставки, который пользователь указывает при оформлении заказа.
email: string — электронная почта для отправки уведомлений и подтверждения заказа.
phone: string — контактный номер телефона, нужный для оперативной связи по вопросам доставки.
Тип TPayment реализован как объединение литералов:
type TPayment = 'card' | 'cash' | ''
Это гарантирует типобезопасность: в поле payment можно передать только одно из разрешённых значений, а пустая строка используется как начальное состояние до выбора способа оплаты.

Модели предметной области
Модель каталога товаров (ProductCatalog)
Класс ProductCatalog отвечает за хранение и управление списком товаров, а также за отслеживание позиции, выбранной для детального просмотра. Он не занимается отображением или сетевыми запросами — только хранением и простой обработкой данных.

Что происходит внутри:

При инициализации создаётся пустой массив товаров и переменная для выбранного элемента (изначально null).
Метод saveProducts загружает в модель весь список товаров.
Методы getProducts и getProductByID позволяют получить доступ к данным — ко всему каталогу или к отдельной позиции по идентификатору.
Для просмотра подробной информации используются методы saveProduct и getProduct: они управляют состоянием «текущего выбранного товара».
Такой подход позволяет отделить данные каталога от логики интерфейса: модель просто хранит состояние, а представление решает, как его показать.

## Модель корзины покупок (ShoppingCart)
Класс ShoppingCart реализует логику корзины: добавление и удаление товаров, подсчёт количества и общей стоимости, проверку наличия позиции.

Особенности реализации:

Корзина хранит массив выбранных товаров.
Метод addSelectedProduct добавляет товар, при этом логика предотвращения дубликатов обычно реализуется внутри (например, по id).
Удаление происходит через deleteSelectedProduct, который фильтрует массив, исключая товар с указанным идентификатором.
Очистка корзины выполняется методом clearShoppingCart, который сбрасывает содержимое в пустой массив.
Подсчёт итоговой суммы делает метод getTotal: он суммирует цены всех товаров, трактуя отсутствующую цену как ноль.
Количество позиций возвращает getSelectedProductsAmount.
Проверка наличия товара по идентификатору доступна через checkSelectedProduct.
Таким образом, корзина — это независимый контейнер данных, который можно использовать в разных частях приложения, не привязываясь к DOM или серверу.

## Модель данных покупателя (Buyer)
Класс Buyer управляет профилем клиента: сохраняет его данные, позволяет их очищать и проверяет корректность перед отправкой заказа.

## Как устроена работа:

Конструктор подготавливает объект с пустыми значениями для всех полей.
Каждый из методов savePaymentType, saveAddress, saveEmail, savePhone обновляет только одно поле, не затрагивая остальные. Это удобно при пошаговом заполнении формы.
Метод getData возвращает полный объект с текущими данными покупателя.
Сброс всех полей в начальное состояние делает clearBuyerData.
Валидация реализована в методе validate: он проверяет каждое поле на заполненность (после обрезки пробелов). Если поле пустое, возвращается текст ошибки; если всё в порядке — пустая строка. Результат — объект с сообщениями об ошибках по каждому полю.
Такая структура делает валидацию прозрачной и удобной для отображения пользователю.

## Слой взаимодействия с сервером (ServerApi)
Класс ServerApi — это прослойка между бизнес‑логикой приложения и удалённым API. Он не хранит состояние и не управляет отображением: его задача — корректно отправлять запросы и возвращать данные в удобном формате.

Принципы работы:

В конструкторе класс принимает экземпляр низкоуровневого API (интерфейс IApi), через который будут выполняться сетевые вызовы. Это пример композиции: ServerApi делегирует реальную отправку запросов другому объекту.
Поле api хранит ссылку на этот клиент, чтобы использовать его в методах.
Метод getProducts обращается к эндпоинту /product/ и возвращает промис с данными о товарах.
Метод postOrder отправляет заказ на эндпоинт /order/ и ожидает подтверждения от сервера.
